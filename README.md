Минималистичный WebSocket-чат на Go. Ноль мьютексов — вся синхронизация 
через каналы. Один бинарник, статика вшита через `embed`.

## Возможности

- 🚀 Мгновенная доставка сообщений через WebSocket
- 👤 Ники пользователей с защитой от пустых имён
- 💬 Служебные уведомления о входе/выходе
- 📦 Один бинарник — `go install` и всё работает
- 🔄 Ping/pong для очистки мёртвых соединений
- 🎨 Встроенный веб-интерфейс — один HTML-файл, без фреймворков и сборки

## Требования

- Go 1.22+

```bash
go install github.com/knorVV/go-ws-chat@latest
```

## Запуск

### Вариант 1: установить и запустить

```bash
go install github.com/knorVV/go-ws-chat@latest
go-ws-chat
```

> **Если команда `go-ws-chat` не найдена:** `go install` кладёт бинарник 
> в `$GOPATH/bin` (обычно `~/go/bin`). Убедитесь, что эта папка в `PATH`:
> 
> ```bash
> export PATH="$PATH:$(go env GOPATH)/bin"
> ```
> 
> Либо запускайте по полному пути: `~/go/bin/go-ws-chat`.

### Вариант 2: запустить из исходников

```bash
git clone https://github.com/knorVV/go-ws-chat.git
cd go-ws-chat
go run .
```

Сервер поднимется на **http://localhost:8080** — откройте в браузере, 
введите ник и начните общаться.

Порт можно переопределить:

```bash
go-ws-chat -addr :9000
# или
go run . -addr :9000
```

## Как это устроено

Классическая схема hub-and-clients, но с парой неочевидных деталей.

### Hub (`hub.go`)

Центральный узел — один goroutine, который обрабатывает все события 
через `select` в бесконечном цикле. Состояние (`clients` — map активных 
соединений) трогает только этот goroutine, поэтому **мьютексы не нужны**: 
гонок нет по построению.

Четыре канала:

| Канал | Назначение |
|---|---|
| `register` | Новый клиент подключается |
| `unregister` | Клиент отключается |
| `broadcast` | Сообщение от клиента — разослать всем |
| `join` | Отдельный канал для «вошёл в чат» |

**Зачем отдельный `join`?** Если рассылать приветствие прямо в `register`, 
новый клиент получит уведомление о собственном входе. Поэтому `register` 
только добавляет в map, а `join` рассылает остальным — через 
`systemMessageExcept(text, client)`, который пропускает самого клиента.

### Защита от медленных клиентов

При отправке в `client.send` используется `select` с `default`:

```go
select {
case client.send <- message:
default:
    close(client.send)
    delete(h.clients, client)
}
```

Если буфер канала переполнен — значит, клиент не успевает читать 
(залипший сокет, медленная сеть). Такой клиент отключается, чтобы 
не блокировать hub. Это защита от head-of-line blocking.

### Client (`client.go`)

Одно WebSocket-соединение — два goroutine:

- **`readPump`** — читает из сокета, отправляет в `hub.broadcast`. 
  Первое сообщение трактуется как ник (чистится через `sanitizeName`). 
  Затем клиент отправляет `hub.join <- c`.
- **`writePump`** — читает из `client.send`, пишет в сокет. Раз в 54 секунды 
  отправляет ping.

Когда `readPump` завершается — отправляет `hub.unregister <- c` и закрывает 
соединение. Когда `writePump` видит закрытый `client.send` — отправляет 
close-фрейм и выходит.

### Батчинг сообщений

В `writePump` есть оптимизация: если в канале `send` накопилось несколько 
сообщений, они отправляются **одним WebSocket-фреймом**, разделённые `\n`:

```go
n := len(c.send)
for i := 0; i < n; i++ {
    w.Write([]byte{'\n'})
    w.Write(<-c.send)
}
```

Это уменьшает количество syscall'ов и сетевых пакетов при всплесках 
активности. Под нагрузкой, когда 10 человек пишут одновременно, вместо 
10 отдельных фреймов уходит 1 — но клиент видит те же 10 строк.

### Таймауты и пинги

| Параметр | Значение | Назначение |
|---|---|---|
| `writeWait` | 10 сек | Таймаут на запись в сокет |
| `pongWait` | 60 сек | Сколько ждём pong от клиента |
| `pingPeriod` | 54 сек (90% от `pongWait`) | Период отправки ping |
| `maxMessageSize` | 512 байт | Максимальный размер входящего сообщения |
| Буфер `send` | 256 сообщений | Если переполнен — клиент отключается |

Ping/pong нужен, чтобы отключать «мёртвые» соединения: если клиент 
закрыл ноутбук, не разорвав сокет, — TCP-соединение висит, а pong 
не приходит. Через 60 секунд сервер закрывает такое соединение.

### Сервер (`main.go`)

HTTP-сервер на стандартном `net/http` (без сторонних роутеров). 
Порт по умолчанию `:8080`, настраивается флагом `-addr`. Статика 
отдаётся через `http.FileServer` из встроенной FS (`embed`).

### Статика (`static.go`)

Статика вшита в бинарник через `//go:embed` (Go 1.16+) — весь клиент 
внутри одного HTML-файла со встроенными CSS и JS, без сборки и внешних 
зависимостей.

Никаких внешних зависимостей, кроме `gorilla/websocket`.

### Клиент

Веб-интерфейс — минималистичный, но с деталями:

- Ник спрашивается через `prompt()` до подключения, обрезается до 32 символов, 
  пустой заменяется на `anon`
- Первое сообщение в WebSocket — ник
- Протокол выбирается динамически: `wss://` для HTTPS, `ws://` для HTTP
- Системные уведомления (вход/выход) начинаются с `***` и отображаются 
  серым курсивом
- Свои сообщения выделяются синим
- Автоскролл к последнему сообщению

## Тесты

```bash
go test -race ./...
```

### Что покрыто

**Интеграционные (`chat_test.go`)** — поднимают реальный `httptest.Server` 
с hub'ом и подключаются настоящими WebSocket-клиентами:

- Уведомление о входе (`*** Пётр вошёл в чат ***`)
- Рассылка сообщения с ником (`Иван: привет`)
- Отправитель получает своё же сообщение
- Уведомление о выходе (`*** Пётр покинул чат ***`)
- Очистка «грязного» ника на сервере (без утечки `\n` в broadcast)

**Unit (`client_test.go`)** — табличный тест `sanitizeName`:

- Обычное имя, пробелы по краям
- Пустая строка и только пробелы → `anon`
- Замена `\n` на пробел, удаление `\r`
- Обрезка длинных имён до 32 символов
- Юникод (`日本語`) не ломается

### Race detector

Тесты запускаются с `-race` — это особенно важно для проекта, где вся 
синхронизация построена на каналах: race detector ловит гонки данных, 
которые могут возникнуть при неправильной работе с горутинами.

GitHub Actions запускается на каждый push и PR в `main`:

- **Build** — `go build -v ./...`

## Ограничения

- **`CheckOrigin` возвращает `true`** — WebSocket принимает соединения 
  с любого домена. Для локального эксперимента удобно, в продакшене 
  нужно ограничить список разрешённых origin'ов.
- **Нет аутентификации** — любой может подключиться и выбрать любой ник.
- **Сообщения не сохраняются** — история чата живёт только в памяти 
  текущих клиентов.
- **Один инстанс** — нет распределённого hub'а, сообщения не ходят 
  между несколькими экземплярами сервиса.
